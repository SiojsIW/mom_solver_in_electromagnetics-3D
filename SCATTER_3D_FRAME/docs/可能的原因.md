这个结果已经很漂亮了：**DIRECTFN 的正确性现在基本站稳了**，RCS 的 RMSE 0.115 dB、最大误差 0.282 dB，和奇异提取法几乎重合。现在剩下的确实就是工程问题——**它为什么慢得这么夸张，以及怎么把 45 分钟压下来。**

我刚才又顺着 DIRECTFN 的实际积分循环看了一遍，发现一个很重要的点：

> 你截图里写的“`N=12 → 每对约 2 万次核求值`”其实明显低估了 DIRECTFN 的工作量。

因为它不是简单做一次 (N^4) 四维 Gauss，而是奇异性消除后还把积分域拆成了多个子域。

### N=12 实际上有多重？

对三角形，源码里的实际 inner Green-function evaluation 数大致是：

| 类型 | DIRECTFN 子域结构     | 单个三角形 pair 的最内层求值次数，N=12 |
| ---- | --------------------- | -------------------------------------- |
| ST   | (3\times 8\times N^4) | **497,664**                            |
| EA   | (9\times N^4)         | **186,624**                            |
| VA   | (2\times N^4)         | **41,472**                             |

ST 源码实际上遍历 3 个 sub-triangles，每个又有 8 个 subranges，然后进入四层 Gaussian integration。 EA 有 6 个大区间，其中前三个各拆成两段、后三个单段，所以总量约 (9N^4)。 VA 每个 ((\theta_p,\theta_q)) 又明确计算两个 ψ 区间，所以是 (2N^4)。

而且每一个最内层点都要重新算 (R)，然后做 `sqrt` 和复数 Helmholtz 指数：

[
G(R)=\frac{e^{-jkR}}{4\pi R}.
]

DIRECTFN 的源码确实是在 inner loop 调 `precompute_rp_rq_data()`，然后 `sqrt` + complex `exp`。

所以你的 45 分钟，我现在反而觉得**完全能解释得通**。

更狠的是，如果你当前 EFIE 对一个 triangle pair 是分别调用：

```text
RWG_WS     → 9 个 vector 项
Constant   → scalar/div 项
```

那么四维积分路径实际上完整走了 **两遍**。

这意味着一个 ST pair 在 N=12 时可能接近：

[
2\times497664 \approx 10^6
]

次 Green-function evaluation。

这已经不是“C++ wrapper 慢一点”的量级了，是真正的计算量巨大。

## 我会按这个顺序优化

1. **先确认你是不是“一对三角形只调用一次 DIRECTFN”。** 这是最重要的检查。`TriangularKernel_RWG_WS` 一次已经直接返回完整 9 个 (I_{ij})，源码 `size()` 就是 9。 所以你的 Fortran 绝对不应该为了 `io=1..3, jo=1..3` 各调用一次 DIRECTFN。

   正确结构应该是：

   ```text
   triangle pair P,Q
          ↓
   DIRECTFN once
          ↓
   Iss(1:9)
          ↓
   scatter 到对应的 3×3 RWG block
   ```

   如果你现在实际上是在 basis-pair loop 里面调用 wrapper，那可以直接得到接近 **9× 加速**。这个必须首先统计：

   ```text
   n_unique_ST_pairs
   n_unique_EA_pairs
   n_unique_VA_pairs
   
   n_DIRECTFN_ST_calls
   n_DIRECTFN_EA_calls
   n_DIRECTFN_VA_calls
   ```

   两边数量应该基本一致，而不是 3×、6×、9×。

2. **DIRECTFN 对象一定要复用，千万不要每个 pair 构造一次。** 这是库作者自己明确强调的：如果连续计算多个 contour，应创建一次 ST/EA/VA object，然后不断 `set(contour)` 重用，避免反复内存分配。([GitHub](https://github.com/thanospol/DIRECTFN?utm_source=chatgpt.com))

   而且我看了源码，`set_Gaussian_orders_4()` 每调用一次会为四维 Gauss 分别重新分配 points/weights——总共 8 个数组——并重新调用四次 Gauss-Legendre 节点生成程序。

   所以如果你的 wrapper 现在类似：

   ```cpp
   extern "C" void directfn_eval(...)
   {
       Triangular_EA<...> alg;
   
       alg.set_wavenumber(k);
       alg.set_Gaussian_orders_4(N);
       alg.set(contour);
       alg.calc_Iss();
   }
   ```

   然后 Fortran 每个 pair 调一次，这是一个明显的性能坑。

   更合理的是：

   ```text
   初始化阶段：
       ST_RWG object
       ST_CONST object
       EA_RWG object
       EA_CONST object
       VA_RWG object
       VA_CONST object
   
       set k0 once
       set Gaussian order once
   
   pair loop:
       object.set(contour)
       object.calc_Iss()
   ```

3. **把 RWG_WS 和 Constant 合成一次 DIRECTFN traversal。** 这个我非常建议你后面做。

   当前这两个 kernel 都使用同一个 Helmholtz

   [
   G(R)
   ]

   区别只是最后乘的 basis factor 不同。DIRECTFN 本身已经在一个 quadrature point 先缓存 Green function，然后计算整个 kernel array。

   但你现在如果分别调用：

   ```text
   TriangularKernel_RWG_WS     size=9
   TriangularKernel_Constant   size=1
   ```

   就把坐标变换、(R)、`sqrt`、`exp` 全算了两遍。

   可以写一个：

   ```text
   TriangularKernel_EFIE_WS
       size = 10
   
       [0..8] → 9 个 RWG_WS
       [9]    → Constant
   ```

   一次积分同时输出：

   [
   (I_{11},\ldots,I_{33},I_{\rm const}).
   ]

   **这一项理论上很接近 2× 加速**，因为真正贵的是四维 traversal 和 complex exponential，多算一个 scalar component 的代价很小。

4. **不要四个方向全用 N=12。** DIRECTFN 本身提供的是：

   ```cpp
   set_Gaussian_orders_4(N1,N2,N3,N4)
   ```

   本来就允许四个方向用不同阶数；相关工作也明确指出，合理选择各维 quadrature order 可以显著改善效率。

   你的成本基本满足：

   [
   T\propto N_1N_2N_3N_4.
   ]

   如果暂时还是统一 N，那么：

   # [ \frac{T_{12}}{T_{10}}

   \left(\frac{12}{10}\right)^4
   =2.07,
   ]

   # [ \frac{T_{12}}{T_8}}

   \left(\frac{12}{8}\right)^4
   =5.06,
   ]

   [
   \frac{T_{12}}{T_6}}
   =16.
   ]

   所以 **12 → 8 不是快一点，而是理论计算量直接降到约 20%**。

   我不会现在直接告诉你生产环境就设 `N=8`，而是建议拿你现在 N=12 作为 reference，对实际 mesh 分别找 10～20 个 ST、EA、VA pair 做：

   ```text
   N=6
   N=8
   N=10
   N=12 reference
   ```

   看完整 9 个 RWG + constant 的误差。

   很可能最后得到类似：

   ```text
   ST : 8
   EA : 8 or 10
   VA : 6 or 8
   ```

   甚至进一步得到：

   ```text
   ST : (8,8,6,8)
   EA : (8,8,8,6)
   VA : (6,6,6,8)
   ```

   只要最终球的 RCS 仍维持现在约 0.1 dB 的水平，就没有必要为了局部积分多出好几个数量级的精度付出 N=12 的代价。

5. **然后上 OpenMP，但并行 triangle pair，不要先并行 DIRECTFN 内部四层 loop。** 每个 ST/EA/VA pair 本来就是完全独立的，这个粒度非常适合并行。

   注意 DIRECTFN object 内部有 `Iss_`、当前 kernel、当前 quadrature state，所以**一个 object 不要被多个线程共享**。

   正确设计是：

   ```text
   thread 0 → 一套 ST/EA/VA contexts
   thread 1 → 一套 ST/EA/VA contexts
   ...
   ```

   每个 thread 初始化一次 Gaussian arrays，然后：

   ```fortran
   !$omp parallel do schedule(dynamic)
   do ipair = 1, npair
       call directfn_eval(context(thread_id), ...)
   end do
   ```

   `dynamic` 比 static 更适合，因为 ST、EA、VA 单 pair 成本差别非常大：大约是

   [
   24:9:2.
   ]

   你如果有 12～16 个物理核心，这里才是把几十分钟真正打下来的地方。

6. **检查有没有重复算 (P,Q) 和 (Q,P)。** 对你现在这个 EFIE weak-singular 部分，

   [
   I(Q,P)=I(P,Q)^T.
   ]

   因此如果 near-field assembler 同时让：

   ```text
   triangle P → Q
   triangle Q → P
   ```

   都进入 DIRECTFN，实际上又浪费了一倍。

   可以只算 unordered triangle pair：

   ```text
   P <= Q
   ```

   然后把 3×3 block 的 transpose scatter 到另一边。

   这一条仅建议用于你已经验证过互易关系的 WS/EFIE 项；以后如果接 `nxRWG_SS` / MFIE，不要未经推导直接这样做。

### 我尤其建议你先查两件事

你的总 Green-function evaluation 数可以粗略写成：

[
N_G \approx
K,N^4
\left(
24N_{\rm ST}
+9N_{\rm EA}
+2N_{\rm VA}
\right),
]

这里：

- (N_{\rm ST})：实际调用的 ST triangle-pair 数；
- (N_{\rm EA})：实际调用的 EA 数；
- (N_{\rm VA})：实际调用的 VA 数；
- (K)：独立 DIRECTFN kernel traversal 次数。现在如果 RWG + Constant 分开，大概率 (K=2)。

你现在只要让程序最后打印：

```text
ST calls =
EA calls =
VA calls =
RWG kernel calls =
CONST kernel calls =

time ST =
time EA =
time VA =
```

我们马上就能算出这 45 分钟到底花在哪。

我还特别怀疑 **ST 会比你直觉里占比高得多**。虽然 ST pair 数少，但一个 ST 的计算量是一个 VA 的：

[
\frac{24}{2}=12
]

倍。

### 45 分钟实际上有机会降很多

我不会先去改 DIRECTFN 的数学算法。现在最值得做的是：

```text
当前：
N=12
可能反复创建 object
RWG / Constant 两遍 traversal
serial
```

改成：

```text
object/context 复用
Gauss nodes 只建一次
每 triangle pair 只调用一次
RWG + Constant fused
N 按 ST/EA/VA 标定
pair-level OpenMP
```

如果经过标定发现 N=8 足够，光 (N^4) 就约 **5×**；再把两种 kernel 融合约 **2×**；再用多核并行，整体从 **45 min 降到几分钟级** 是完全现实的。具体能到多少要看你的 pair 数、CPU 和当前 wrapper 有没有重复计算，不能简单把所有倍率相乘。

还有一点：**Fortran↔C++ 的函数调用本身现在根本不是主矛盾。**一次 EA/ST 调用内部几十万次积分点计算，ABI 那几十纳秒/几百纳秒完全淹没了。现在应该先砍算法调用次数和 (N^4)，而不是折腾接口微优化。

如果是我现在接着改这个工程，我第一步会直接打开 `DIRECTFN_WRAPPER.cpp`，看三个地方：**每次 wrapper 是否 `new`/构造对象、是否每次 `set_Gaussian_orders_4()`、以及一个 triangle pair 到底调用几次 wrapper。** 这三个一看，基本就能判断你这 45 分钟里面有没有一个很大的“白送性能坑”。
